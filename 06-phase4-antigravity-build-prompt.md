## Goal for this phase

Build the full Task module: schema, screens, manual task creation, and the automation engine that lets admins configure "when a deal enters stage X, auto-create task Y" — wired into the existing `onDealStageChanged` hook. Also implement a due/overdue notification mechanism.

## 1. Schema — create these Firestore collections

```
Task
  id (doc id)
  agencyId: string
  ownerAgentId: string          // who the task is assigned to
  ownerHierarchyPath: string    // same visibility pattern as Lead/Deal
  createdByAgentId: string | null   // null if system/automation-generated
  relatedLeadId: string | null
  relatedDealId: string | null
  title: string
  description: string | null
  dueAt: timestamp
  priority: 'low' | 'medium' | 'high'
  status: 'open' | 'completed'
  completedAt: timestamp | null
  autoGenerated: boolean        // true if created by a StageTaskTemplate rule
  sourceTemplateId: string | null  // which StageTaskTemplate created this, if any
  createdAt, updatedAt: timestamp

StageTaskTemplate
  id (doc id)
  agencyId: string
  triggerStageId: string        // FK -> PipelineStage; fires when a deal enters this stage
  taskTitle: string             // may include a simple placeholder like {{contactName}}
  daysUntilDue: number          // relative to the moment the deal enters the stage
  priority: 'low' | 'medium' | 'high'
  active: boolean
  createdAt, updatedAt: timestamp
```

`status` does not store `'overdue'` — overdue is **derived**, computed as `status == 'open' && dueAt < now()`, both for querying (a Firestore query on `status == 'open'` + `dueAt < now` composite) and for display (red badge). Do not add a stored overdue status that requires a background job to keep in sync.

## 2. Screens to build

1. **My Tasks** (`/tasks`) — list of tasks visible to the viewer (own tasks always; managers/admins also see downline tasks via the visibility rule, in a toggle: "My Tasks" vs "Team Tasks"). Filter by status (open/completed/overdue — overdue computed client-side), priority, and due-date range. Default sort: overdue first, then soonest due. Each row: title, priority badge (capsule), due date/relative time ("Due today", "3 days overdue" in red), linked lead/deal name as a clickable chip, and a checkbox to mark complete inline without opening the task.
2. **Task quick-add** — a global "+" affordance (e.g., in the top bar) opens a lightweight modal: title, due date/time, priority, optional link to a lead or deal (searchable dropdown). Available from anywhere in the app.
3. **Task creation from Lead/Deal detail pages** — add a "New follow-up task" button to the existing Lead detail (Phase 2) and Deal detail (Phase 3) pages. This is an additive UI touch point only — pre-fills `relatedLeadId`/`relatedDealId` and opens the same quick-add modal. Do not alter existing Lead/Deal logic beyond adding this button.
4. **Task detail / edit** — click a task row to expand or open a side panel: full description, edit any field, mark complete/reopen, delete (with confirmation).
5. **Automation rules settings** (`/settings/task-automation`) — admin-only. List of `StageTaskTemplate` rules per pipeline stage, with create/edit/deactivate controls. Show `triggerStageId` as the stage's actual name (join with `PipelineStage`), not a raw ID.
6. **Dashboard widget** — a compact "Due today / Overdue" card on the main dashboard (dashboard itself may not fully exist yet; if it doesn't, create a minimal dashboard route and place this widget there) showing count of overdue and due-today tasks for the viewer, linking into `/tasks` pre-filtered.

## 3. Manual task validation
- `title` and `dueAt` are required. `dueAt` must be a valid date/time; for **manually created** tasks in the quick-add modal, warn (not block) if the chosen due date is in the past — some legitimate follow-ups get logged retroactively, so this is a soft warning, not a hard validation error.
- If `relatedLeadId` or `relatedDealId` is set, verify the referenced doc exists and is within the creating agent's visibility scope before allowing the link.

## 4. Automation engine — implement the `onDealStageChanged` hook body

Replace the no-op in `dealAutomationHooks.ts` with:
1. Query `StageTaskTemplate` where `agencyId == deal.agencyId`, `triggerStageId == toStageId`, `active == true`.
2. For each matching template, create a `Task`:
   - `ownerAgentId`: `deal.ownerAgentId` (assign to the deal's owner)
   - `ownerHierarchyPath`: `deal.ownerHierarchyPath`
   - `relatedDealId`: `deal.id`, `relatedLeadId`: `deal.leadId` if present
   - `title`: `template.taskTitle` (simple placeholder substitution: replace `{{contactName}}` with the linked lead/deal's contact name if the placeholder is present)
   - `dueAt`: now + `template.daysUntilDue` days
   - `priority`: `template.priority`
   - `autoGenerated: true`, `sourceTemplateId: template.id`, `createdByAgentId: null`
3. **Idempotency**: before creating, check whether a `Task` already exists with the same `dealId` + `sourceTemplateId` + a `dueAt` within the same stage-entry window (e.g., created within the last minute as part of this same transaction batch) — this guards against the hook firing twice due to a retried transaction. Practically: perform the template-driven task creation inside the same Firestore transaction as the stage-change write in Phase 3's board code, so it's atomic with the move itself, not a separate async call that could double-fire.
4. If a deal **re-enters** a stage it was already in before (e.g., moved back from Underwriting to Application Submitted, then forward again), the automation fires again and creates a new task — this is intended, not a bug; each stage entry is a fresh trigger.

Seed one sensible default `StageTaskTemplate` on agency creation (or as a migration): trigger stage = `Application Submitted`, title = `"Check underwriting status for {{contactName}}"`, `daysUntilDue: 5`, `priority: 'medium'`.

## 5. Due/overdue notification mechanism
- Implement a scheduled Cloud Function (daily, e.g. 7am agency-local time if timezone is tracked, otherwise a single fixed UTC time is acceptable for v1) that queries all `Task` docs where `status == 'open'` and `dueAt` falls within "today" or is already in the past, groups them by `ownerAgentId`, and sends a single digest email per agent (not one email per task — avoid spamming).
- In-app: the dashboard widget (section 2.6) reflects due/overdue counts live via a direct Firestore query on page load — this does not depend on the scheduled function, which is for email only.
- Notification/email failures must never block or roll back task creation or completion — log the failure, do not throw it back into the user-facing flow.

## 6. Firestore Security Rules to add
- `Task` reads/writes: same visibility pattern as `Lead`/`Deal` — allowed if `ownerAgentId == request.auth.uid` OR requester's `hierarchyPath` is a prefix match of `resource.data.ownerHierarchyPath`.
- `StageTaskTemplate` writes restricted to `role in ['admin']` for that `agencyId`; reads open to any agent in the agency (the automation logic and settings display both need to read them; only admins mutate).
- Reject `Task` writes missing `title` or `dueAt`.

## 7. Error states to implement and manually verify before calling this done
- [ ] Quick-add modal validates required fields inline; past-due date shows a soft warning, does not block submit
- [ ] Marking a task complete updates instantly (optimistic UI) with a checkmark/strikethrough animation within the 150–250ms motion budget; rolls back with an error toast if the write fails
- [ ] Linking a task to a lead/deal outside the creator's visibility is rejected before the task is created
- [ ] Automation-created tasks appear correctly assigned to the deal's owner, not the agent who dragged the card (if a manager moved a deal on an agent's behalf, the task still goes to the deal's owner)
- [ ] Re-entering a stage creates a new automation task rather than being silently skipped or erroring
- [ ] Automation task creation does not double-fire under a retried/concurrent stage-change transaction — verify with a forced retry test
- [ ] Deactivating a `StageTaskTemplate` stops new tasks from being generated but does not delete/alter previously created tasks
- [ ] An agent cannot see, edit, or complete a task outside their downline (verify via direct SDK read attempt — expect permission-denied)
- [ ] Scheduled email digest failure (e.g., email provider down) is logged and does not affect task creation/completion in the app
- [ ] Dashboard widget and `/tasks` list never show a blank/frozen state on load — skeleton first, then data or an explicit empty state ("No tasks due — you're all caught up")

## 8. Definition of done
- Tasks can be created manually (quick-add, from Lead, from Deal) and automatically (stage-triggered templates)
- Admins can configure, edit, and deactivate stage-task automation rules without needing engineering help
- Overdue/due-today states are computed correctly and surfaced both in the task list and a dashboard widget
- Daily email digest sends correctly, grouped per agent, and failures are isolated from core task functionality
- Every checklist item in section 7 manually triggered and confirmed
- Visibility rule verified identical to Lead/Deal: managers see downline tasks, agents see only their own

Do not build commission tracking or reporting in this phase — that is Phase 5 and Phase 7 scope.
